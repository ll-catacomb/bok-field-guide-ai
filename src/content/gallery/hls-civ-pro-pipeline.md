A course-specific AI tool is only as good as the text behind it: a chatbot that hallucinates citations or misreads § symbols is worse than no chatbot at all, and the gap between a generic LLM and a useful one is almost entirely the quality of the corpus it can ground itself in. To make that infrastructure available to a high-stakes doctrinal course, the Learning Lab partnered with the HLS Civil Procedure team to build [civil-procedure-materials](https://github.com/bok-learning-lab/civil-procedure-materials), a shared GitHub repository with a strict folder convention (`original/` for raw sources, `cleaned/` for UTF-8 Markdown), an `inventory.csv` master tracker, and six custom Claude Code skills (`/clean-pdf`, `/clean-scan`, `/clean-docx`, `/clean-slides`, `/clean-transcript`, `/qa-check`) that walk a TA through extraction step by step. The repo also ships with a one-hour zero-to-first-cleaned-file setup guide and a TA cheatsheet that condenses the workflow to a single page. As a first pass through the system, the team extracted Professor Greiner's full annotated *Civil Procedure* casebook (Version 02) into 26 chapter Markdowns — roughly 8,500 lines of structured text — via a single `/clean-docx` invocation, with case names italicized, citations preserved, and page anchors retained as HTML comments. The design choice that matters most is who does the work: TAs, not engineers, run the pipeline, which means the corpus grows at the natural rate of a teaching team and the law school retains the conversion craft after the project ends.

The hardest part of building a course-specific AI tool is rarely the AI. The model layer is a commodity, the prompts are tractable, and the user interface is a weekend's work. What is genuinely difficult — and what most "we should have a chatbot for this course" conversations skip past — is the corpus: the body of clean, machine-readable text the AI will be grounded against. A chatbot that confidently hallucinates the holding of *International Shoe* is worse than no chatbot at all, especially in a doctrinal course where the cost of a misread citation is a student internalizing bad law. The Learning Lab's work with the HLS Civil Procedure team is, in that sense, infrastructural rather than glamorous: the goal is not to ship the chatbot, but to make the chatbot — and the practice question generator, and the essay-feedback system, and whatever else the course wants next — possible.

The shape of the work is a shared GitHub repository, [bok-learning-lab/civil-procedure-materials](https://github.com/bok-learning-lab/civil-procedure-materials), in which every category of course material has the same internal structure: an `original/` folder where raw sources are dropped and never modified, and a `cleaned/` folder into which UTF-8 Markdown is extracted. The categories are course-shaped — casebook, lectures, exams, assignments, study-aids, outline — and the top-level `inventory.csv` tracks every item's status, reviewer, and date. None of this is novel as filesystem convention; what makes it work is the discipline of maintaining it, and the tooling that makes maintaining it cheap.

That tooling is a set of six Claude Code slash skills, written specifically for this repo and committed alongside the materials in `.claude/commands/`. `/clean-pdf` extracts text-selectable PDFs and inserts page anchors as HTML comments; `/clean-scan` runs vision-based OCR on scanned PDFs and flags uncertain spots; `/clean-docx` converts Word documents and strips tracked changes and conversion chrome; `/clean-slides` extracts both text and diagram descriptions; `/clean-transcript` segments raw lecture transcripts into headings; `/qa-check` runs a post-conversion sweep for encoding, citation, and structural problems. Each skill is a few dozen lines of Markdown — a checklist a TA can read — and each enforces the same conventions: YAML frontmatter, italicized case names, preserved § symbols, page anchors as HTML comments, footnotes as Markdown footnotes. The skills are paired with planned `batch-*` agents that can run any of the same conversions across an entire category in parallel once a TA has confirmed that the manual single-file path works.

The first pass through the system has already produced a substantial artifact: Professor Greiner's full annotated *Civil Procedure* casebook (Version 02) extracted into 26 chapter Markdown files — front matter, twenty-four day-by-day chapters, and an acknowledgments file — totalling roughly 8,500 lines of structured text. Case names are italicized, the table of authorities renders correctly, page breaks are preserved as `<!-- page: N -->` anchors, and the casebook's day-by-day pedagogical sequence is intact. That single conversion is the proof of concept the rest of the corpus can now scale against.

The design decision that matters most, though, is who runs the pipeline. The repository is built around the assumption that TAs, not Bok engineers, will be the people typing `/clean-pdf` for the next dozen exams and the next semester's lectures. To make that real, the repo ships with a [setup guide](https://github.com/bok-learning-lab/civil-procedure-materials/blob/main/_context/setup.md) that walks a brand-new TA from "I have never opened a terminal" through Xcode Command Line Tools, VS Code, the Claude Code extension, cloning the repo, and processing their first PDF — in about an hour. A separate one-page TA cheatsheet, distilled from the longer reference guide, lives at the level a TA can read in five minutes between classes. The bet is that AI infrastructure for a course is sustainable only if the people closest to the course can maintain it; an external engineering team that converts every new exam by hand is a bottleneck the course will eventually route around.

The work is also a careful piece of FERPA hygiene. The repository's three load-bearing rules are written into the cheatsheet, the README, and the `CLAUDE.md`: do not upload student work, grades, or student-identifiable material to external AI tools; save your work to the repository rather than to chat; start with one file of each type and work through it manually before trying to automate. Student-identifiable material is excluded from the open repo entirely and lives only in an access-controlled location; the public corpus is the casebook, the exam prompts, the model answers, the slides, and the lecture recordings — the things students are already given access to as part of the course.

The strategic frame this project sits inside is the Bok Center's broader stance on Generative AI: that AI's most durable contribution to a course is rarely the visible chatbot, but the invisible infrastructure that lets a faculty member's own materials remain authoritative when AI is in the room. A clean corpus is the difference between an AI that speaks the casebook and an AI that speaks whatever the open web absorbed about civil procedure. The casebook-conversion work is a precondition for any of the more visible AI projects the course might want next, and the repo is structured so those next projects can begin without rebuilding the substrate. In that sense the deliverable is not the cleaned text — it is the apparatus that produces clean text on demand, owned and operated by the law school's own teaching staff.
